## 1. Постановка задачи

Исходное требование (дословно по смыслу): полностью переписать `TerrainTileShema` и
реализовать автотайлинг по принципу Terraria для оригинальных тайлсетов `Tiles_0` (земля)
и `Tiles_1` (камень):

- учитывать 4 стороны **и диагонали**, края, внешние/внутренние углы, полностью окружённые блоки,
  переходы земля↔камень, варианты текстур;
- не менять генерацию карты, хранение блоков, атласы и посторонние механики;
- архитектура должна позволять добавлять новые блоки без переписывания движка;
- предусмотреть локальное обновление кадров при установке/удалении блока;
- проверить отсутствие ошибок компиляции;
- главный приоритет — **правильное визуальное соединение**, а не скорость.

Позже требования уточнялись: сверяться именно с **Terraria 1.4.4.9**, не подгонять координаты
под картинку, не менять ожидания тестов без доказательства.

## 5. Серия жалоб и итераций

Далее было ~7 раундов с уточнениями и скриншотами из игры. Ниже — что делалось и
**чем закончилась каждая гипотеза**. Это самая важная часть отчёта: несколько
«исправлений» оказались ошибочными и были отменены.

### Раунд A. «Слияния не всегда работают»

- **Гипотеза A1**: merge-кадры не применяются, потому что Block 3 считал соседа-землю
  границей → введена `IsConnected(slot) = (slot == SlotSelf || slot == SlotMerge)` и
  использована в Блоке 3; флаги `merge*` стали выставляться безусловно.
- **Итог: ОШИБОЧНО.** Это и была главная регрессия (см. §6). Гипотеза держалась
  несколько раундов, потому что давала «визуально бесшовные» блобы камня в земле.

### Раунд B. «В игре тоже неправильно»

- **Гипотеза B1**: 3×3 перерисовки недостаточно (окно 5×5) → добавлены
  `RedrawWorldTile5X` в `IScreenUpdateManager`/`ScreenUpdateManager` и вызов для слоя 0
  в `TileDataProvider.ChangeTile` и `SetTile`.
- **Итог: логически верно** (не проверено в плеере). Сохранено.

### Раунд C. Три дефекта: камень на земле, угол пещеры, конец вертикальной полоски

- Правки того же `IsConnected`, плюс добавление веток 2д/2е в Блок 2.
- **Итог:** часть веток совпала с оригиналом случайно, часть дублировала существующие.

### Раунд D. Рекомендации «агента-критика»

Применено: поле `MutualMergeCheckDiagonalIsSelf`, гейт `anyMerge` в Блоке 1.
Отвергнуто: `anySelf` в Блоке 2 — при его включении **3 теста упали**
(одиночный камень в земле терял merge-кадр), правка отменена.
**Вывод:** рекомендации «на глаз» без сверки с декомпиляцией опасны.

### Раунд E. «Камень не сливается с ровной поверхностью земли»

- Добавлен `TerrainGrass` в `Stone.mergeTypes`.
- **Итог:** для проекта полезно (на поверхности карты трава), но это **отклонение**
  от оригинала (в 1.4.4.9 трава для камня дала бы `Edge`). Зафиксировано в
  `TECHNICAL_ANALYSIS.md` §6.2.

### Раунд F. «Первый кадр полоски камня неверный»

- **Гипотеза F1**: для `up=Merge, down=Merge, left=Edge, right=Self` нужен кадр
  `(126, 144+18v)`.
- **Итог: ОШИБОЧНО.** Пиксельный анализ кадра показал: `(126,144)` рисует землю сверху и
  **тёмную рамку снизу**, т.е. это кадр «слияние сверху, низ — граница». Декомпиляция
  подтвердила: `(126, 144..180)` выдаётся в ветке 76227 при `up==-2` и `left==right==-1`,
  а не для нашей конфигурации.
- Промежуточно проверялась и другая ошибочная ветка: кадр выбирался как `(108,216)`
  (ветка 76207), что тоже не соответствует конфигурации.

### Раунд G. Финальная сверка (последний раунд)

Перечитан `WorldGen.cs` целиком по нужным диапазонам и построена полная карта веток.
Найдено **5 конкретных расхождений** (см. `TECHNICAL_ANALYSIS.md` §7), из них главное —
`IsConnected` в Блоке 3. Реализация переписана точным переносом, добавлена таблица
всех 57 веток, всё проверено.

## 6. Итоговая причина (доказанная)

`IsConnected()` в Блоке 3 считала `SlotMerge` соединённым. В оригинале generic-цепочка
(76564–76927) сравнивает **строго** `== num`, поэтому `-2` ведёт себя как пустота.

Для `up=Merge, down=Merge, left=Edge, right=Self`:

```
Блок 1:  left == -1            → не входит
Блок 2:  75964 … 76384         → ни одна ветка не подходит
         (76041 входит, но подветки 76043/76062 требуют up/down == num)
Generic: 76873 (up≠num, down≠num, left≠num, right==num) → (162, 18v)
```

Со `IsConnected` реализация попадала в ветку «левый край» → `(0, 18v)`.
Отсюда «неправильный первый кадр» на скриншотах.

Доказательство: `references/WorldGen_TileFrame_1.4.4.9_extracts.md` §8, §10.

## 7. Ошибки и проблемы в процессе работы (важно для следующей модели)

### 7.1 Порча файла построчными правками из PowerShell

Несколько раз `TerrariaFraming.cs` правился удалением/вставкой диапазонов строк
(`RemoveRange`/`InsertRange`). Это привело к:

- дублирующимся закрывающим скобкам (`CS1519`, `CS1022`, `CS8641`);
- «съеденным» блокам `else if` (потерянные ветки);
- рассинхронизации отступов.

**Вывод:** для этого файла нельзя применять построчные правки — только `edit` по
уникальному контексту или полная перезапись через `write`.

### 7.2 Двойная кодировка (UTF‑8 → CP1251)

Файл был сохранён так, что русские комментарии превратились в мусор
(`РџСЂР°РІРёР»Р°`). Это мешало читать код и путало при правках. Исправлено полной
перезаписью в UTF‑8.

### 7.3 Скрипты PowerShell 5.1 и .ps1 без BOM

`render_preview.ps1` с русскими комментариями не парсился в Windows PowerShell 5.1
(`Unexpected token`), потому что файл читался как ANSI. Решение: сохранять `.ps1`
в **UTF‑8 с BOM**. Также: `pwsh` (PowerShell 7) в этой среде отсутствует — запускать
через `powershell -File`.

### 7.4 Грабли GDI+ при рендере дампов

- `New-Object System.Drawing.Bitmap($w*16*2, ...)` → `op_Multiply` не найден;
  нужно считать арифметику заранее и приводить к `[int]`.
- `New-Object System.Drawing.Rectangle($x,$y,$w,$h)` → неверный биндинг;
  нужно `-ArgumentList`.
- `InterpolationMode = NearestNeighbor` + `PixelOffsetMode = Half` — иначе тайлы «мылятся».
- При неверном `PixelOffsetMode` пиксельный анализ кадров давал **ложные** «коричневые»
  области на стыках — это на короткое время привело к ошибочной гипотезе о содержимом
  merge-кадров. Правильный анализ — `GetPixel` по кадру без масштабирования.

### 7.5 Тесты, закреплявшие неправильное поведение

Часть ожиданий в `Program.cs` была получена «по факту работы» и закрепляла ошибочные
кадры (`(0,0)` для торца полосы, `(234,0)` для камня с землёй по бокам, флаги
`mergeU/D` у generic-кадров). При финальной сверке они были **заново выведены из
декомпиляции**, с указанием номера ветки в тексте теста.

### 7.6 Диагностика, дававшая ложную тревогу

`Diagnostic.cs` считал «проблемой» любой generic-кадр при наличии merge-соседа.
По оригиналу это **норма** для непокрытых комбинаций. Метрика переименована в
информационную.
