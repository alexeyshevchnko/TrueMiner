# План рефакторинга TrueMiner

Основание: [Docs/Architecture.md](Architecture.md). Спорные места, требующие решения
человека, вынесены в [Docs/Decisions.md](Decisions.md).

**Приоритеты:** К — критический, В — высокий, С — средний, Н — низкий.
**Проверка:** «код» — прочитано напрямую, «модуль» — прочитано в ходе модульного прохода
по исходникам, «⚠» — выведено статически, в рантайме не подтверждено.

Главный критерий отбора: правка должна либо убирать падение, либо снижать стоимость
сопровождения, не меняя поведение в штатном сценарии. Всё, что меняет поведение, помечено
и требует решения.

## 1. Критические и высокие

### В-1. `GOPool.Spawn<T>` падает без подходящего кэша — **ВЫПОЛНЕНО**

- **Статус:** выполнено, см. `Docs/Decisions.md` D-11 (принят вариант 1). **Коммит:** `8e8cb2a`.
- **Где:** `Assets/Generator/core/utils/GOPool.cs:169-181` (`Spawn<T>`);
  `:140-153` (`Spawn(prefab)` — там ленивое создание кэша есть);
  `:28` (`ObjectCache.Type = prefab.GetComponent<IBasePoolObject>()`)
- **Что было неисправно:** в `Spawn<T>` переменная `cache` оставалась `null`, если ни один кэш
  не совпал по типу, и сразу вызывался `cache.GetNextObjectInCache()` (`:179`) → NRE.
  Ленивое создание кэша **по типу T невозможно**: у `Spawn<T>` нет префаба, из которого
  можно было бы инстанцировать объект, — есть только тип.
- **Что сделано:** перед обращением к `cache` добавлена проверка, которая бросает
  `InvalidOperationException` с именем типа `T` и подсказкой, куда добавить кэш.
  Путь выполнения при найденном кэше не изменён.
- **Проверено по коду:** кэши создаются только для предметов: `PrefubManager.InitItems` →
  `IgoPoolManager.AddCache` (`PrefubManager.cs:22-27`, `GOPoolManager.cs:23-27`).
  Эффекты и подписи (`BloodEffect`, `LightPointEffect`, `ArrowEffect`, `BoomEffect`,
  `JungleRemoveEffect`, `BlockPoolBagItem`, `GuiLbl`) в кэш из кода не добавляются —
  они берутся из списка `GOPool.caches` сцены. В `MainScene.unity` такие записи есть:
  `GuiPool` (объект с `RedLbl.prefab`) и `GOPool` (9 префабов: Blood, Boom, block, TorchItem,
  LightEffect4, LightPointEffect, BloodDead, JungleRemoveEffect, ArrowEffect).
  Для YAML-префабов состав скриптов сверен и совпадает с запрошенными типами.
- **Почему это правильное исправление:** падение в горячем пути урона, смерти и копания
  (около 20 вызовов `Spawn<T>`) заменено на явную и точную диагностику. Поведение при
  корректно настроенных кэшах не меняется, поэтому риск регрессии минимален.
- **Затрагивает:** пулы эффектов, `GuiLbl` (подписи урона), `BloodEffect`, `LightPointEffect`,
  `JungleRemoveEffect` (копание), `BlockPoolBagItem`.
- **Проверки:** компиляция `Assembly-CSharp` (201 файл из `.csproj`) — 0 ошибок и до, и после
  правки; все вызовы `Spawn<T>` просмотрены; diff — 4 добавленные строки.
- **Осталось непроверенным:** `Boom.prefab` и `RedLbl.prefab` — бинарные (Unity 2017, без YAML),
  поэтому текстовый поиск `m_Script` в них не работает; наличие в них компонентов
  `BoomEffect` / `GuiLbl` можно подтвердить только в Unity. Проверка в Play Mode не выполнялась
  (редактор Unity был занят проектом).

### В-2. Переполнение буфера физики — **ВЫПОЛНЕНО**

- **Результат:** `BufferItem` берёт ёмкость из параметра `size` (раньше было жёстко 100) и
  растёт при `Add`, если запрос покрыл больше тайлов, чем ёмкость (раньше — `IndexOutOfRange`).
  Публичные сигнатуры и кольцевая семантика (`Count`/`Reset`) не менялись.
  Потребители (`Collision.cs`) используют только `Count`, индексатор и `Add` внутри `Collision`.
- **Проверки:** компиляция `Assembly-CSharp` (201 файл из `.csproj`): 0 ошибок, 0 предупреждений
  до и после. Diff — 10+/2−. BOM и CRLF сохранены.
- **Не проверено:** реальный объём запросов в игре (через `Pick`/`Axe`/`Shell` с `includingAll`), Play Mode.
- **Исходная проблема (для истории):**
- **Где:** `Assets/Generator/Physics/BufferList.cs:76-80`, `BufferItem(int size)` (`:61-68`)
- **Что:** каждый `BufferItem` создаёт ровно 100 слотов, параметр `size` игнорируется;
  `Add` пишет `Items[Count]` без проверки. `BufferList` создаётся без аргументов
  (`Collision.cs:8`), значит лимит — 100 записей в одном прямоугольном запросе.
- **Почему чинить:** `IndexOutOfRangeException` в разрешении коллизий обрывает
  `PhysicItem.Update` на этот кадр; при `includingAll: true` (`Pick.cs:166`, `Axe.cs:76`,
  `Shell.cs:18`) достаточно большого прямоугольника. Плюс `GetCollidersInRect` возвращает
  общий буфер (`Collision.cs:153`), поэтому его нельзя держать между вызовами.
- **Как:** использовать `size` по назначению и/или расти по `Capacity`, сохранив кольцевую
  семантику. Не менять сигнатуры `Add`/`NextBuffer` — это вызовет цепочку правок.
- **Затрагивает:** коллизии кирки, топора, снарядов, зомби.
- **Проверка:** код.

### В-3. Разыменование `PlayerController` до его создания — **ВЫПОЛНЕНО**

- **Результат:** `PlayerController` отсутствует до `CreatePlayer()`. Проверки добавлены там, где
  поведение без игрока определено однозначно:
  - `Flag.FixedUpdate` — без игрока видимость не обновляется (раньше NRE каждый физический шаг);
  - `TargetManager.OnChangeMap` — не двигает игрока, которого ещё нет (игрок создаётся позже
    в `CreatePlayer` ровно в `MapGenerator.CenterPos`);
  - `TargetManager.GetUnitsInRange` — игрок не попадает в список целей взрыва;
  - `Backsword.DoDamage` — импульс отдачи не применяется без игрока; урон и эффект крови — применяются;
  - `Bag.AddBagItem` — подпись над игроком не создаётся, предмет в сумку добавляется всегда;
  - `ZombieBehaviour.UpdateDirect` — направление не меняется; перезапуск кулдауна сохранён (см. С-17).
- **Не тронуто (вне В-3, отмечено):** `PlayerComtext.cs:31,34`, `BagItemContext.cs:19,32` — вызываются
  из UI сумки; нужно подтвердить, что UI не открывается без игрока (см. «Осталось непроверенным»).
- **Причина, а не маскировка:** порядок инициализации не менялся; `CreatePlayer` выполняется как раньше.
- **Проверки:** компиляция `Assembly-CSharp` (201 файл из `.csproj`): 0 ошибок, 0 предупреждений.
  Diff: 22+ / 8−, BOM и CRLF совпадают с HEAD.
- **Не проверено:** Play Mode (взрыв до спавна игрока, флаг при старте сцены).

### В-3 (исходная формулировка)

- **Где:** `src/Items/Flag.cs:22` (в `FixedUpdate`), `src/weapons/Backsword.cs:115`,
  `src/Bag.cs:81`, `src/TargetSystem/TargetManager.cs:42, 207`
- **Что:** `PlayerController` присваивается только в `CreatePlayer()` (`TargetManager.cs:66`).
  В перечисленных местах нет проверки на `null`; в `Flag` — ещё и в каждом физическом шаге.
- **Почему чинить:** NRE на кадр, если флаг существует или взрыв случился раньше спавна игрока.
  `GetUnitsInRange` (`:207`) вызывается из `ExplosionDamage`, то есть любой взрыв до спавна
  игрока падает.
- **Как:** проверка `PlayerController != null` в каждом месте; в идеале — единая точка доступа.
  Логику порядка инициализации не менять.
- **Затрагивает:** флаги, взрывы, подбор предметов.
- **Проверка:** код.

### В-4. Юниты не попадают в трекинг — **ВЫПОЛНЕНО**

- **Результат:** `CreateUnit` и `CreateMinerUnit` сами добавляют юнит в `units`; внешние
  `units.Add(...)` в `OnTick` убраны (иначе была бы двойная регистрация). `DestroyUnit` теперь
  безусловно снимает юнит из списка и уничтожает `gameObject`, а не ищет его циклом.
- **Почему это не меняет текущую игру:** оба пути сейчас не исполняются — `MapGenerator.StartApplication`
  начинается с `return`, а `maxUnitts = 0`. Правка устраняет утечку на момент, когда любой из
  путей будет включён (см. D-2, механики не включались).
- **Проверки:** компиляция: 0 ошибок, 0 предупреждений. Diff: 7+ / 9−.
- **Не проверено:** поведение при включённых шахтах и спавне юнитов (по условию задачи не включались).

### В-4 (исходная формулировка)

- **Где:** `src/TargetSystem/TargetManager.cs:113-123` (`CreateUnit`),
  `:125-135` (`CreateMinerUnit`), `:137-145` (`DestroyUnit`)
- **Что:** `CreateUnit` возвращает контроллер, не добавляя его в `units`; добавление делает
  вызывающий код (`:188`, `:190`). `CreateMinerUnit` не добавляется **нигде**, поэтому
  `DestroyUnit` не находит юнит и не уничтожает `GameObject`.
- **Почему чинить:** утечка объектов, «мёртвые» юниты продолжают тикать. Сейчас путь
  недостижим (`StartApplication` начинается с `return`, `maxUnitts = 0`), но он оживёт
  при включении любой из этих веток.
- **Как:** добавлять в `units` внутри `CreateUnit`/`CreateMinerUnit`, убрать внешние `units.Add`,
  в `DestroyUnit` уничтожать `gameObject` безусловно.
- **Затрагивает:** спавн и смерть юнитов, `OnTick`, урон по площади.
- **Проверка:** код.

### В-5. Повторный `CreatePlayer` при переключении мир/дом — **ВЫПОЛНЕНО**

- **Принято:** D-5, вариант 2 — при переключении игрок пересоздаётся, но предыдущий экземпляр
  уничтожается. Так сохраняется текущее поведение сброса игрока при смене карты (подтвердить его
  смену на «перенос» я не могу), а утечка исчезает.
- **Результат:** в `CreatePlayer` перед созданием нового игрока старый снимается с `otherPlayers`
  и уничтожается. `PlayerController.OnDestroy` (`PlayerController.cs:162-167`) отписывает
  `OnCollision` и вызывает `pysicItem.Destroy()`, поэтому выгрузка корректна.
  `AddInfinityCooldown(OnTick)` теперь регистрируется один раз (`tickRegistered`), а не на каждое
  переключение — раньше тики дублировались.
- **Проверки:** компиляция: 0 ошибок, 0 предупреждений. Diff: 11+ / 1−.
- **Не проверено:** Play Mode (переключение мир/дом, поведение камеры и HP после смены карты).

### В-5 (исходная формулировка)

- **Где:** `src/TargetSystem/TargetManager.cs:35` (`OnGenerate += OnMapGenerate`),
  `:45-61`; `MapGenerator.cs:141-142`
- **Что:** подписка не снимается. `ChangeMap()` вызывает и `OnChangeMap`, и `OnGenerate`,
  поэтому `OnMapGenerate` срабатывает на каждое переключение и заново создаёт игрока,
  перезаписывая `player` без уничтожения старого, и добавляет ещё один `OnTick`.
- **Почему чинить:** дубли игрока и тиков; ⚠ в рантайме не проверялось, но следует из кода.
- **Как:** идемпотентность `CreatePlayer` (если игрок уже есть — выйти) либо снятие подписки
  в `OnDestroy`. Выбор между вариантами — в `Decisions.md`.
- **Затрагивает:** игрок, камера (`Camera.main.transform…TargetChase`), тики.
- **Проверка:** модуль, ⚠.

### В-7. Кэш размеров карты в `Collision` не инвалидируется — **ВЫПОЛНЕНО**

- **Проверки:** компиляция: 0 ошибок, 0 предупреждений. Diff: 9+ / 19−.
- **Не проверено:** Play Mode (копание сразу после переключения мир/дом).

### В-7 (исходная формулировка)
